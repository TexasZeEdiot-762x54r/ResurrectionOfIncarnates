CIRCLE CREATION CRASH FIX

The old server acknowledged setupCircle with empty data. Native request type 57
immediately dereferences data.sv_circle and reads sv_circleId, causing C0000005.
The creation reply now contains the Circle and its initial leader/member record.
getCircleInfo additionally needs data.sv_invitings at the response root, while
sv_members belongs inside data.sv_circle. Supplying invitations only inside the
Circle caused the subsequent native type-60 parser to dereference a null array
at 0x14008eb98. The root array is now returned and checked by the client adapter.
The screen also issues getTagName and getPlayerState. Their compatibility
responses include data.sv_tagNames=[] and data.sv_states=[] respectively. Empty
data={} for getTagName caused another null-array crash at 0x140091205. No named
teams or presence states are invented; those services remain unimplemented.

Invite-menu loading issues: browsing friends can request many remote profiles
at once. Optional appearance reads now allow at most eight starts per ten
seconds and two in flight, with a bounded 32-entry cache (two seconds for a
valid profile, five for a missing/unavailable profile). Excess reads return the
existing explicit-default guest appearance, not another player's outfit; a
later read can retry. This leaves headroom under the unchanged TLS connection
limits for essential Circle and lobby traffic. No friends are removed and no
profiles are written by this cache. The tunnel logs local admission refusals
without including friend IDs, credentials or addresses.

Implemented: create, information, member list, search, name lookup, leader setting
changes, disband, and nonleader leave. Identical creation retries reuse the record.
Both the client patch and the shared server update are required.

Storage: Circle tables share the existing bounded commendations SQLite database
and persistent Docker volume. Profile uploads cannot overwrite membership.
Own membership is refreshed at login and own-profile loads and after Circle calls.
No account level, XP, LP, cosmetics, cubes or layouts are granted or reset.

Not implemented: joining/invitations, subleaders/leadership transfer,
Circle chat/rankings/rewards. These mutations return NG, not fake OK.
Invitation collection loads remain empty. This is not a fully restored guild system.

Revival safety limits (not recovered original rules): 1024 Circles, 20 initial members,
100-member expansion ceiling,
64-byte names, 255-byte comments; PNG emblems up to 96 KiB of base64 text and
512x512 dimensions. Requests are bounded at 128 KiB; client responses at 2 MiB.
The native game sent a roughly 74 KB creation request with its emblem; the prior
16 KiB request / 4 KiB icon caps incorrectly rejected it with native error9009.
Search sends summaries without full member/invite arrays so 20 large emblems
still fit the bounded response. Small synthetic ==== tests had missed this.
Search pages are one-based with 20 rows, matching observed native requests.
Zero remains a first-page alias only for older diagnostic callers. Area/rank zero
means no filter. enableMaxMember is ignored. Native wire roles are 2=leader,
1=subleader, 0=member; no nonleader joining or subleader assignment is enabled.
Creation has no charge; authentic original creation pricing has not been recovered.

2026-10-20 search, permissions and intermittent crash correction:
The native first search sent sv_page=1 while the old server skipped 20 records.
It returned sv_totalPage=1 and an empty array even when the Circle matched.
Both name search and ID-based search now return the first page correctly.
The old leader position 1 displayed Sub Leader and hid leader-only settings.
Parser 0x14008e8fa maps wire 2/1/0 to internal roles 1/2/3; manager 0x14031d715
enables leader controls only for internal role 1. Membership is not migrated:
the stored authoritative leader determines the corrected response position.

An independent local HTTP race caused the latest Circle-tab native crash at
0x140091205: concurrent per-request importlib.reload cleared the handler table,
sometimes returning data={} for getTagName instead of sv_tagNames=[]. A bounded
160-read loopback repro returned 29 missing arrays before the correction and
zero afterward. server.py now imports handlers normally and never reloads them
per request. Restart the local profile server when deploying handler changes.
This does not bypass native parser checks, add presence/team data or relax TLS
limits. Neither an executable patch nor a profile/currency reset is required.

The v20 member-capacity popup was not a working purchase: its NG rejection
caused native fatal error 9009. That attempt did not deduct LP or add capacity.

2026-10-20 v21 member-capacity purchases:
The user explicitly approved 10,000 LP for 5 slots, matching native popup
instructions at 0x14031ad34..0x14031ad40. This is adopted revival policy, not
proof of the original production economy. Only the authoritative leader may
expand, up to the 100-member revival safety ceiling. Native request 72 is
incMaxNumOfMembers with empty data; success requires data.sv_maxMembers (string)
at parser 0x14008f01b. Both client and shared server must be updated together.

The local adapter reserves LP and writes circleCapacityPending atomically before
sending its generated operation ID and expected capacity to the shared backend.
The SQLite backend changes capacity and records the result in one transaction.
Repeated operation IDs return their durable receipt, never another expansion.
Expected-capacity checks reject competing stale requests; leader/identity checks
remain server-side. No existing membership, icon, comment, rewards or levels reset.

Lost/invalid replies keep the reservation for reconciliation with the same
operation on retry, including after restart. A valid rejection receipt refunds
once. Never delete a pending journal or manually refund an uncertain operation:
it might already have committed remotely. A permanently unavailable backend or
exhausted receipt storage needs operator reconciliation. Receipts are bounded
to 16,384 records plus the existing approximately 64 MiB SQLite storage ceiling.
Two-second native repeats reuse the last response because the original request
contains no operation ID; wait two seconds before another intentional purchase.
The local wallet is read on the next profile load; an already open UI may cache it.

LP remains local to each installation, and anonymous public mode trusts claimed
identities and local profiles. This is NOT a tamper-proof centrally verified
economy. Private mode retains its existing per-identity credentials. Test purchases
use synthetic profiles only; installing v21 does not debit any real account.
Your previous failed purchase is not replayed automatically. Invitations remain
unfinished, and the complete native purchase UI still needs a user test.

2026-10-20 v22 Sub Leader allowance purchases:
incMaxNumOfSubLeaders previously returned NG, causing another fatal 9009 error.
That failed attempt did not debit LP. The native popup selects increment 1 at
0x14031abc3 and cost 10000 at 0x14031ad40. The new revival purchase uses these
displayed values, with a 10-slot safety ceiling (not a recovered original limit).
Only the leader may purchase. Native request 71 has empty data; its response
must contain sv_subLeaderNum as a numeric string (parser 0x14008ef7d). Later
Circle information uses sv_subLeaderMax. These are not interchangeable fields.

Shared Sub Leader capacity and receipts are stored separately from member slots.
Both use the same transaction and local-LP reservation checks, with a combined
16,384-receipt safety cap and rejection of cross-kind operation reuse. Local
journals are circleSubLeaderCapacityPending / circleSubLeaderCapacityReceipt;
existing member journals keep their old keys and pending v21 operations remain
recoverable. Immediate two-second retries are coalesced independently per kind.
Lost replies keep reservations; only matching confirmed rejections refund them.
The member-slot 5-for-10000 policy is unchanged.

Purchasing increases the ALLOWANCE only: no member is automatically promoted,
no membership or member capacity changes, and no LP is granted. changeSubLeader,
leadership transfer and invitations remain unimplemented. The local LP balance
is still installation-specific and public identities are unverified. New schemas
do not reset existing Circles or purchases. Deployment does not charge users or
replay their failed attempts. Native UI purchase confirmation remains pending.

Public access remains anonymous with claimed IDs, NOT verified Steam identities.
Private mode requires the caller's configured identity credential for mutations.
Do not treat the public backend as a secure identity or paid-economy service.

Source-derived API examples and responses are in ROI-API.json/ROI-Client-API.json.
